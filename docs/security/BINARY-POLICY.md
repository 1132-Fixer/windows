# Binary policy

Every binary that ships inside a 1132 Fixer release is either built from source
in this repository or has documented provenance: what it is, where it came from,
its licence, why it ships, and who owns the decision.

Two things are kept separate throughout, because conflating them produces false
statements in both directions:

- **Currently packaged binaries** — what a user actually receives today.
- **Historical binaries in git history** — blobs reachable from old commits but
  absent from `HEAD`. These do not ship. They are recorded here for provenance,
  not as an inventory of the product.

---

no longer ships `libEGL.dll` or `libGLESv2.dll`; those names were removed from

### 1.3 First-party native components

**None.** 1132 Fixer ships no first-party compiled code. All first-party logic
is JavaScript inside `resources/app.asar`, plus two PowerShell scripts delivered
through `extraResources`:

| File | Purpose |
| --- | --- |
| `resources/zoom-firstrun-setup.ps1` | Prepares the helper account's first Zoom launch |
| `resources/grant-media-consent.ps1` | Grants camera/microphone consent for the helper account |

These are source, not binaries, and are reviewed as source. They are listed here
because they are the only executable content outside the Electron runtime and
the asar, and because the packaging allowlist has to permit them by exact path
(see [`../development/release-process.md`](../development/release-process.md)).

One, and it was found by building the package inventory rather than by reading
the source — which is the reason the inventory exists.

| Binary | `resources/elevate.exe` |
| --- | --- |
| SHA-256 | `9b1fbf0c11c520ae714af8aa9af12cfd48503eedecd7398d8992ee94d1b4dc37` |
| Size | 107,520 B |
| Version | `1, 0, 0, 2894` — "Elevate Application", company "Johannes Passing" |
| Origin | electron-builder's NSIS resource bundle, cached locally as `nsis-3.0.4.1/elevate.exe` |
| Licence | Elevate, by Johannes Passing — permissive; attribution belongs in `NOTICE.md` |
| Why it ships | electron-builder still copies it into `win-unpacked` for `perMachine` NSIS. First-party code does not call it. `build/installer.nsi` sets the uninstaller to `RequestExecutionLevel admin` so uninstall UAC is Windows, not this helper. `customInstall` deletes it from `$INSTDIR\resources` after extract. |
| Signed | **No** — `NotSigned`, like everything else this project ships today |
| Owner | The `electron-builder` version in `devDependencies` |

Two things follow that are worth stating rather than leaving implicit:

- It is **not resolved through `package-lock.json`**. electron-builder downloads
  its NSIS resource bundle at build time into a machine-level cache. A hosted
  runner fetches it fresh on every release. That is a build-time supply-chain
  dependency outside the lockfile, and the inventory check is currently the only
  thing in this repository that would notice if the file changed.
- Its hash is recorded above precisely so a change is visible. If a build
  produces a different hash for `resources/elevate.exe`, treat it as a
  supply-chain event and investigate before releasing — do not simply update the
  number.

No other third-party DLL, `.node` addon, driver, or bundled tool is packaged.
Adding one requires a row in this section before it may ship, and
`build/package-allowlist.json` must be extended by exact path in the same pull
request.

belt-and-braces against reintroduction.

## 3. Rules for adding a binary

A binary may be added only when all of the following are true, recorded in the
pull request that adds it:

1. **Built from source here**, with the build reproducible from a documented
   command — *or* fetched from a named upstream release.
2. **Provenance**: upstream project, exact version, and download URL.
3. **Licence**: identifier and compatibility with this project's MIT
   distribution, plus any attribution the licence requires added to `NOTICE.md`.
4. **Purpose**: what breaks without it, and why a source-level alternative is
   not viable.
5. **Hash**: SHA-256 of the exact file, recorded in §1 of this document.
6. **Owner**: who is responsible for tracking its upstream security advisories.

Then extend `build/package-allowlist.json` by exact path in the same pull
request. A binary that reaches the shipping artifact without an allowlist entry
fails CI by design — that failure is the control working, not an obstacle to
route around by broadening the allowlist pattern.

## 4. What is never packaged

`build/package-allowlist.json` fails the build if any of these reach the
shipping artifact without an explicit, path-exact entry:

`.exe` · `.dll` · `.msi` · `.sys` · `.node` · `.ps1` · `.bat` · `.cmd` ·
`.key` · `.pfx` · `.pem` · `.p12` · `.cer` · `.crt` · `.env` · `.db` ·
`.sqlite` · `.zip` · `.7z`

Certificates and keys have no legitimate entry: they must never exist in the
repository at all, so an allowlist entry for one is never the correct fix.
